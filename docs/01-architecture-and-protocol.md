# Qoder 桌面版逆向分析（一）：包结构与通信协议

> 分析对象：Qoder-win-x64-user.exe（产品版本 0.4.3，构建 2026-09-26，217,982,176 字节，md5 491f7c5bdb8a744e56e4839ffb7048d6）
> 本文中的所有结论均可在本仓库的输入产物上复现，未标注“待确认”的条目为已验证。

## 1. 安装包分层

安装器是 NSIS 自解压（PE32 x86 GUI，ProductVersion 0.4.3），内部只有一个真正的负载：`$PLUGINSDIR/app-64.7z`（217,001,607 字节）。解开后得到 Electron 应用的完整目录树，共 508 个文件、223 个目录，解压尺寸约 716MB。

应用主体是 `resources/app.asar`（141,352,046 字节，内部 4658 个条目）。另有 `resources/app.asar.unpacked/` 存放原生模块与需要真实文件系统路径的资源，`resources/bin/` 存放若干自研原生插件。

## 2. 进程与代码分层

Qoder 是 Electron 应用，代码分为四块。

主进程是 `out/main/index.js`（12,234,878 字节），负责窗口、IPC、认证、本地服务管理。预加载脚本为 `out/preload/*.cjs`，例如 `pluginViewRuntime.cjs`（2,571,345 字节）。渲染层是 `out/renderer/assets/index-*.js`（20,777,438 字节）加上大量按需加载 chunk。

第四块也是最有价值的一块：agent 运行时。它位于 `node_modules/@qoder-ai/qoder-agent-sdk/dist/_worker/qoder-worker-runtime.obf.mjs`（33,191,719 字节），来自内部产品 `qodercli`，版本 1.1.64，构建于 2026-09-25T18:55:20Z，源提交 `8928898`，CI 身份 `aoneci`（阿里内部流水线），目标平台 win32-x64。同一目录还包含 `proto/chat.proto`、`runtime-info.json`、`builtin/` 技能包与 `vendor/qoder-security/` 安全扫描插件。

原生模块方面，除了第三方库（node-pty、@napi-rs/canvas、sharp、keytar、photon-node），自研的有 `resources/bin/native_clipboard.node`、`notification_permission.node`、`dji_mic_button.node`、`appshot_bare_modifier_monitor.exe`，以及 `aoq-electron-sdk` 提供的 `aoq_node_ext.node` 与 `AoqClientSdk.dll`。经符号检查，AoqClientSdk 是阿里云 RTC 音视频 SDK（导出 `AoqClientEngine::createEngine`、`AoqConnectConfig`、`IAudioFrameObserver` 等），与 Qoder 业务逻辑无关，仅有语音通话用途。

结论：Qoder 的业务逻辑约 99% 位于 JS/TS 产物中，Ghidra 一类反编译器在这里的用武之地仅限于那几个自研小体积原生模块。

## 3. 模型通信协议（已还原）

`proto/chat.proto`（8,366 字节）直接给出了模型通道的完整定义。

服务定义为 `ChatService`，包含两个 RPC：`ChatCompletion`（一元）与 `ChatCompletionStream`（服务端流式，每个消息为一个 SSE chunk）。proto 包名为 `model.chat`，Java 包名为 `com.qoder.grpc.model.chat`。

请求体 `ChatCompletionRequest` 与 OpenAI Chat Completions 高度对齐：model、messages、temperature、top_p、max_tokens、stream、stop、presence_penalty、frequency_penalty、n、user、seed、logit_bias、tools、tool_choice、response_format、modalities、stream_options。在此之上 Qoder 做了几处自有扩展。

第一处是推理强度 `Reasoning.effort`，取值 UNSPECIFIED、NONE、LOW、MEDIUM、HIGH、XHIGH、MAX，共七档。

第二处是 `patches` 字段（`map<string, ChatPatchList>`），这是一套前缀缓存补丁机制。`ChatPatch` 带 `cache_id`、`action`、`position`、`content`、`name`、`rename_to`、`description`、`parameters`，说明客户端会对历史消息做增量修改而不是整体重发，`ChatMessage.cache_id` 与 `Tool.cache_id` 是这套机制的锚点。

第三处是 `ChatMetadata`，分四个域。`WorkspaceMetadata` 描述工作区：file_count、languages、codebase_status、codebase_soft_status、codebase_external_id、data_policy，其中 codebase_external_id 指向服务端的代码库索引实体。`BusinessMetadata` 描述业务上下文：id、name、begin_at、product、version、type、stage、sub_task。`ContextMetadata` 用于链路追踪与客户端标识：request_id、session_id、task_id、request_set_id、machine_id、client_type、source_session_id。`UserMetadata` 只有 user_id。

第四处是 `Advisor`（name、model、max_uses）与 `CustomModelConfig`（name、url、style、provider、model、parameters），后者即自带密钥（BYOK）接入自定义模型或网关。

响应侧定义了 `ChatCompletionResponse` 与流式 `ChatCompletionChunk`，都带 `code`、`id`、`object`、`created`、`model`、`choices`、`usage`、`extras`。`Usage` 细分 `PromptTokensDetails.cached_tokens/cacheable_tokens` 与 `CompletionTokensDetails.reasoning_tokens`，可见服务端按缓存命中与推理 token 分开计费统计。

## 4. 客户端接入的域名

主进程与 worker 产物中出现的 Qoder 服务端点包括：openapi.qoder.sh、api2.qoder.sh、center.qoder.sh、gateway.qoder.com.cn、openapi.qoder.com.cn，另有 test 前缀的测试环境（test-api2.qoder.sh、test-openapi.qoder.sh、test-gateway.qoder.com.cn、test.qoder.ai）。企业侧存在 VPC 私有端点形态，字符串中给出示例 `acme.vpc.qoder.com.cn`，并支持保存该端点。

worker 产物还引用了 dashscope.aliyuncs.com（阿里云百炼模型服务），说明模型后端可切换至阿里云侧通道。

## 5. 模型提供方抽象

worker 内部按 provider 形态分支，字符串中出现 anthropic、openai、openai-responses、openai-compatible、anthropic-compatible 以及 qodercli 自有形态。这意味着 agent 运行时的模型层是一个多协议适配器，而非只对接自家网关。

## 6. 信息通道与本地状态

worker 字符串显示存在名为 `cacheInterceptorV3` 的本地 SQLite 表，字段包含 body、deleteAt、statusCode、statusMessage、headers、etag、cacheControlDirectives 等，即是说客户端的 HTTP 响应缓存由一张可失效的拦截器表承载。

另有 `exports dashboard`（Qoder Insights Report，HTML 报告，页脚标注 Generated by Qoder CLI）、`--dangerously-skip-permissions` 等 CLI 开关，以及一条针对 pkill 的保护逻辑：脚本会识别并拒绝掉会误杀 Qoder CLI 自身的 pkill 调用。

## 7. 与移动端的联动

字符串中包含“下载 Qoder Mobile 并登录同一账号，自动接管此会话”的中英文文案，说明桌面端与移动端通过同一账号实现会话接管。

## 8. 待确认项

主进程 `out/main/index.js` 中的 IPC 通道命名、登录/令牌刷新流程、本地服务与端口约定尚未完成结构化提取，将在下一轮分析中补齐。33MB worker 产物的反混淆（prettier 结构化 + 字符串表解密）已在 CI 中执行，结果将用于还原 agent 主循环、工具集与提示词体系。
